**Fecha:** 2026-10-02  
**Rama:** `sweep/consolidacion-ux-v1`  
**Base:** `main` en `42b36410460bbd75d7c3582f6447261ba54b6e76`  
**Alcance:** consolidación estructural, compatibilidad, CI, rutas web, autenticación y defectos transversales de baja complejidad. No se modifica `main`.

## Resultado ejecutivo

La auditoría encontró un bloqueo de verificación que debe resolverse antes de declarar estable el producto: el último workflow disponible de `main` (01/10/2026, ejecución [36805939919](https://github.com/martinezmarcos93/tortuscript/actions/runs/36805939919)) ejecutó 585 tests y terminó con **116 failures, 47 errors y 2 skipped**. La dependencia se instaló correctamente; la etapa de tests falló y el validador de contenido quedó omitido por la interrupción del workflow.

La evidencia del log muestra una divergencia grande entre las pruebas web históricas y el nuevo contrato Cuenta adulta → sesión → ChildProfile. Varios tests esperan páginas educativas con HTTP 200 sin sesión, pero el middleware actual redirige a `/cuenta/ingresar` (302); varios tests de API esperan 403 por token o 403/404 de lógica previa, pero el middleware de identidad responde 401 antes. Otros tests manipulan directamente `persistencia_local`, mientras que la app actual obtiene el contexto y progreso desde `RuntimeEducativo` y `ProgresoChildProfile`.

Esto no demuestra que todos los fallos sean defectos del producto: sí demuestra que la suite completa no representa de forma consistente la arquitectura actual y que no existe una señal CI verde verificable. No se deben ocultar estos fallos ni reducir la cobertura para conseguir un verde artificial.

## Cambios aplicados en este barrido

### 1. Compatibilidad de Python en el limitador de login

En `web/cuenta_routes.py`, la clave del limitador de intentos se construía con una f-string que reutilizaba comillas dobles dentro de una expresión. Esa forma depende de la gramática ampliada de f-strings de Python 3.12, mientras que README declara compatibilidad con Python 3.9 o superior.

Se extrajo la normalización a una variable previa:

```python
email_normalizado = email.strip().lower()
limit = _limit_or_429(
    f"login:{request.remote_addr}:{email_normalizado}", 10, 900
)
```

El comportamiento buscado no cambia: el bucket de rate limit usa el correo normalizado, sin distinguir mayúsculas ni espacios externos. La modificación elimina esa dependencia innecesaria de sintaxis reciente.

### 2. CI de la rama de trabajo

Se actualizó `.github/workflows/verificar-fase0.yml` para ejecutar la verificación al hacer push a `sweep/consolidacion-ux-v1` y en pull requests dirigidos a `main`. Esto evita que el barrido dependa de una ejecución manual o de ramas históricas.

La suite completa ya tenía fallos en `main`; por eso el workflow se usa como detector de regresiones, no como evidencia anticipada de éxito. Hay que leer y clasificar el siguiente resultado real.

## Segundo pase: orden de controles HTTP

El análisis de la suite confirmó un defecto concreto adicional en `web/app.py`: el middleware de identidad educativa se ejecutaba antes que el control del token local de la API. Por eso, una petición a `/api/*` sin token podía recibir 401 por falta de sesión en lugar de ser rechazada primero por el gateway con 403. Son controles distintos y deben ejecutarse en orden: validación del Host/token local primero; resolución de la sesión y ChildProfile después.

**Corrección aplicada en la rama:** se reordenaron los dos hooks `before_request` sin eliminar ni debilitar ninguno de los controles. Se añadió una prueba de regresión en `tests/test_cuenta_routes.py` que diferencia:
- API sin token: 403.
- API con token local válido, pero sin sesión educativa: 401.

Esta prueba todavía necesita ejecución confirmada en CI. No se afirma que la suite completa haya mejorado hasta disponer de un resultado posterior a estos commits.

## Hallazgos P0 — bloquean la declaración de estabilidad

1. **Suite completa roja.** 116 fallos y 47 errores en la última ejecución disponible.
2. **Contrato de autenticación desalineado en pruebas antiguas.** Tests de `test_web.py`, `test_camino.py`, `test_accesibilidad.py` y `test_proyectos.py` todavía asumen acceso educativo sin sesión o progreso local legacy.
3. **Falta una prueba de integración canónica del ciclo comercial-educativo.** Debe cubrir registro/verificación/login, creación y selección de ChildProfile, onboarding, lección, guardado de progreso, logout y aislamiento entre perfiles.
4. **No se obtuvo verificación local independiente.** El entorno de trabajo no puede resolver `github.com` para clonar el repositorio; los resultados de tests deben obtenerse en CI o en una máquina con el repositorio disponible.
5. **El validador de contenido no corrió en la última ejecución CI**, porque el job se detuvo al fallar la etapa de tests.

## Hallazgos P1 — primer barrido funcional

1. Revisar los errores de tests que no se explican por redirección a login; no etiquetar automáticamente todos los errores como obsoletos.
2. Migrar fixtures y helpers de tests al contrato Cuenta/ChildProfile/RuntimeEducativo, conservando tests unitarios del modelo local solo donde corresponda.
3. Alinear expectativas de códigos HTTP: distinguir falta de sesión (401), falta de autorización/CSRF/token (403) y recurso inexistente (404).
4. Ejecutar el validador de contenido, tests JavaScript, contraste y responsive de forma separada para obtener resultados por dominio aunque una suite falle.
5. Verificar Python 3.9 además de la versión usada actualmente en CI; README declara soporte desde 3.9.

## Hallazgos P2 — limpieza y consistencia

1. Mantener separados los tests del runtime local histórico y los tests del runtime comercial por perfil.
2. Revisar referencias a `persistencia_local` en tests web para identificar cuáles son deliberadamente legacy y cuáles deberían migrarse.
3. Actualizar los documentos de auditoría anteriores como antecedentes, sin sobrescribirlos ni tratarlos como evidencia de CI actual.
4. Completar la matriz responsive en navegadores reales/Playwright; una matriz documentada no equivale a una matriz ejecutada.

## Decisión técnica

No se recomienda reabrir el diseño curricular ni agregar nuevas funcionalidades mientras la suite y sus fixtures no distingan claramente el runtime local del runtime autenticado por perfil. La siguiente tanda debe concentrarse en reparar el contrato de pruebas y en corregir fallos reales que sobrevivan a esa migración, no en reescribir la arquitectura ni en silenciar las pruebas.
