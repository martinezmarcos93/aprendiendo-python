# Auditoría UX/UI V1 — TortuScript

**Rama:** `audit/ux-v1-2026-09-30`  
**Base:** `main` @ `5a107c8bb362e3ae6abf36043f9a3c3a5f64c656`  
**Fecha:** 2026-09-30  
**Alcance:** auditoría estática del flujo web actual, plantillas, CSS, JavaScript, rutas y pruebas existentes. No se modifica `main`.

## 1. Estado general

TortuScript ya tiene una interfaz web considerablemente desarrollada. No estamos ante una maqueta: existe navegación, onboarding, recorrido curricular, ejercicios, lecciones por pasos, editor de código, traducción a Python, Tortuga, TortuGame, proyectos, proyectos integradores, práctica/repaso, mapa, logros, liga, resumen, referencia, accesibilidad y perfiles locales.

La arquitectura actual sigue siendo la de una aplicación local. Esto es coherente con el estado actual del producto, pero no debe confundirse con la futura arquitectura comercial definida en ADR-029..037.

La auditoría confirma que el trabajo inmediato no debería ser una reconstrucción completa de la UI. Conviene conservar el sistema visual existente y corregir primero los puntos que afectan navegación, uso táctil, editores, jerarquía y futura migración comercial.

## 2. Flujo actual observado

Flujo principal:

`Inicio → Aprender → Lección → pasos → resultado → siguiente lección`

Flujos paralelos:

- Experimentar → editor → ejecutar → guardar → Mis proyectos.
- Zona Tortuga → editor → lienzo → guardar → Mis proyectos.
- Juegos → editor → escena → registro → guardar.
- Proyectos integradores → etapas → archivos → validación → exportación.
- Practicar → tarjetas → repaso.
- Más → Mapa / Repaso / Logros / Liga / Resumen / Referencia / Ayuda.
- Perfil → cambio de perfil / exportación / importación.
- Ajustes → tamaño / contraste / tipografía / movimiento / voz.

El flujo es funcionalmente rico, pero la cantidad de superficies hace que la navegación principal tenga una densidad alta para el público infantil.

## 3. Fortalezas confirmadas

### P0 — Base visual coherente

Existe un sistema de diseño centralizado en `web/static/css/tortu.css`, con tokens para colores, tipografías, superficies, bordes, radios y controles.

Esto permite evolucionar la UI sin introducir un framework ni duplicar estilos.

### P0 — Accesibilidad ya considerada

Se encontraron:

- enlace "Saltar al contenido";
- `focus-visible`;
- soporte de tamaño de texto;
- alto contraste;
- tipografía legible;
- reducción de movimiento;
- lectura por voz;
- roles ARIA;
- diálogos;
- etiquetas para canvas;
- soporte de teclado;
- foco explícito en partes del flujo de lección.

No conviene eliminar estos mecanismos durante el rediseño.

### P0 — Responsive ya implementado

Existen breakpoints a 900, 800, 700, 600, 460 y 380 px.

Hay adaptación específica para:

- navegación;
- hero;
- editores;
- lienzos;
- estadísticas;
- mapa;
- proyectos integradores;
- diploma;
- reducción de movimiento.

Por lo tanto, la tarea correcta es validar y endurecer el responsive existente, no construirlo desde cero.

### P0 — Aislamiento de ejecución

La aplicación local ya utiliza token para sus API locales, restricciones de Host y CSP. Los juegos utilizan Worker y el editor web usa iframe sandbox.

Para la futura versión comercial habrá que sustituir el modelo local por el backend/sandbox definido en ADR-031 y ADR-033, pero la separación conceptual existente es aprovechable.

### P0 — Persistencia y perfiles

El producto ya posee una noción de perfil, progreso, exportación/importación y ajustes por perfil. Esto será útil como antecedente para la futura separación Cuenta adulta → Perfiles.

## 4. Hallazgos críticos

### UX-01 — Falta validación real en dispositivos móviles
**Prioridad: CRÍTICA**

El CSS demuestra intención responsive, pero una auditoría estática no permite garantizar el comportamiento real en:

- Android 320–390 px;
- iPhone 375/390 px;
- teclado virtual abierto;
- orientación vertical;
- interacción táctil prolongada;
- selección de código;
- desplazamiento mientras se edita;
- canvas táctil;
- modales.

Antes de considerar cerrado el bloque móvil hay que realizar pruebas reales o automatizadas sobre estas condiciones.

**Acción:** crear matriz de pruebas mobile y ejecutarla sobre Inicio, Lección, Ejercicio, Tortuga, Juegos, Proyectos y Proyecto Integrador.

### UX-02 — Los controles pequeños no garantizan objetivo táctil de 44 px
**Prioridad: ALTA**

`.boton.chico` reduce tipografía y padding y varios enlaces de navegación también utilizan dimensiones compactas. Visualmente funcionan en escritorio, pero el objetivo táctil mínimo debe validarse.

**Acción:** establecer una regla explícita para controles interactivos principales en móvil. No necesariamente todos los controles deben ser gigantes; los controles secundarios pueden mantener densidad si disponen de separación suficiente.

### UX-03 — CodeMirror tiene alturas fijas
**Prioridad: ALTA**

El editor general usa aproximadamente 300 px; otros modos usan 180–260 px.

En escritorio esto es razonable. En móvil, con teclado virtual abierto, el espacio útil puede reducirse drásticamente.

**Acción:** validar editor + teclado. Si hace falta, usar alturas adaptativas en móvil y una estrategia clara de foco/scroll.

### UX-04 — La barra superior concentra demasiada información
**Prioridad: ALTA**

En escritorio reúne:

- navegación;
- racha;
- nivel;
- XP;
- sonido;
- ajustes;
- perfil.

En móvil existe menú colapsable, lo cual es correcto, pero las estadísticas siguen siendo parte de la misma estructura.

**Acción:** en la próxima iteración móvil separar conceptualmente:
1. navegación;
2. estado del jugador;
3. acciones de sistema.

No necesariamente requiere una reescritura visual inmediata.

### UX-05 — La navegación principal presenta demasiadas opciones al mismo nivel
**Prioridad: ALTA**

Actualmente aparecen directamente:

Inicio, Aprender, Experimentar, Tortuga, Juegos, Proyectos, Practicar y Más.

Para un usuario infantil, "Aprender" debería ser claramente el eje principal. Experimentar, Tortuga y Juegos son espacios complementarios.

**Acción:** estudiar una jerarquía de navegación donde el recorrido educativo sea dominante y las herramientas creativas queden como espacios secundarios sin perder accesibilidad.

## 5. Hallazgos importantes

### UX-06 — Inicio tiene buena información pero mucha competencia visual
**Prioridad: MEDIA**

La pantalla combina:

- bienvenida;
- progreso;
- XP;
- racha;
- meta diaria;
- reto;
- práctica;
- liga;
- experimentar;
- Tortuga;
- encuesta;
- camino completo de cursos.

Es una pantalla rica, pero puede resultar cognitivamente cargada.

**Acción:** priorizar visualmente una única acción primaria: "continuar aprendiendo". El resto debe funcionar como información secundaria.

### UX-07 — El mapa y el camino cumplen funciones parcialmente superpuestas
**Prioridad: MEDIA**

Inicio contiene el camino curricular y existe además un Mapa de progreso.

**Acción:** definir explícitamente:
- Inicio = "qué hago ahora";
- Mapa = "dónde estoy y qué existe";
- Resumen = "cómo me fue".

No eliminar ninguna superficie todavía.

### UX-08 — Tortuga y Juegos son experiencias completas, no simples extras
**Prioridad: MEDIA**

Ambas superficies tienen editor + visualización + ejecución + feedback y, en algunos casos, persistencia.

Deben tratarse como productos internos coherentes, no como páginas aisladas.

**Acción:** compartir patrones de editor, ejecución, feedback y guardado.

### UX-09 — Proyecto Integrador tiene una estructura pedagógica fuerte
**Prioridad: MEDIA**

La separación por etapas, archivos, validación y ayudas desbloqueables es apropiada para la progresión hacia Croco-Script.

**Acción:** conservar el patrón como antecedente para Croco-Script, evitando trasladar innecesariamente su complejidad al primer nivel infantil.

## 6. Hallazgos de arquitectura comercial

### ARCH-01 — La UI actual sigue siendo local
**Prioridad: BLOQUEADA POR ARQUITECTURA**

La aplicación expone token de sesión local al frontend y mantiene perfiles/progreso localmente.

Esto es correcto para el producto actual, pero no debe evolucionar accidentalmente hacia una falsa "cuenta online".

La migración debe seguir ADR-029..037:

`Cuenta adulta → Perfiles → Suscripción → Entitlements → TortuScript / Croco-Script`

### ARCH-02 — El token local no debe convertirse en mecanismo de autenticación comercial
**Prioridad: CRÍTICA PARA LA MIGRACIÓN**

El mecanismo `X-Tortu-Token` sirve para proteger la aplicación local. No debe reutilizarse como sustituto de sesiones comerciales, identidad o entitlement.

La futura plataforma deberá utilizar sesiones seguras y autorización servidor-side.

### ARCH-03 — El progreso local necesita contrato antes de sincronizarse
**Prioridad: ALTA**

Actualmente el progreso está profundamente integrado con el modelo local.

Antes de cloud/sync debe definirse un contrato versionado que permita compartir progreso con Croco-Script sin importar internals de TortuScript.

## 9. Decisión de trabajo

No se recomienda un rediseño total.

La estrategia de esta rama será incremental:

**Auditar → corregir P0 → probar → corregir P1 → probar → comparar con main → PR → revisión → merge.**

La rama no debe introducir todavía autenticación comercial, pagos ni cloud. Esos cambios pertenecen a los bloques arquitectónicos correspondientes y no deben mezclarse con la auditoría visual.

## 10. Próximo bloque técnico

El siguiente trabajo de esta rama debe ser la creación de una matriz de pruebas UX automatizables para las rutas críticas:

`/`
`/bienvenida`
`/aprender`
`/leccion/<id>`
`/ejercicios/<n>`
`/experimentar`
`/tortuga`
`/juego`
`/proyectos`
`/proyectos-integradores`

La primera corrección de código debería atacar el comportamiento mobile y los controles táctiles, no cambiar todavía la identidad visual.

## 11. Limitación de esta auditoría

Esta primera pasada fue una auditoría estática del código de la rama. No equivale todavía a una prueba manual con navegador real a 320/375/390/768 px ni a una prueba con teclado virtual de Android/iOS.

Por eso los hallazgos marcados como problemas de comportamiento móvil deben considerarse hipótesis técnicas de alta prioridad hasta ser verificados en ejecución.
